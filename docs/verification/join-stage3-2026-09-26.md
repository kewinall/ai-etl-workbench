## V2 規格與精確 Join 語意攔截（程式層）

新增獨立 `EtlSpecificationV2`，不改寫 V1 schema。V2 明確要求兩個不同且順序固定的
source_refs，以及完整 Join 契約。現有 `validate_specification`／`compile_hpl` 入口已接上
語意檢查，INNER／LEFT、鍵值或節點 ID 與已確認輸入不符時，回傳：

- `SPEC_JOIN_SEMANTICS_MISMATCH`
- `field_path`（例如 `joins.0.join_type`）
- `requirement_path`（例如 `join_contract_v1.joins.0.join_type`）
- `node_id`、`proposed_node_id`
- `expected`、`actual`（僅 schema-validated 語意欄位）

測試從真實 compiler 入口注入 LEFT→INNER，確認沒有 HPL、plan 或可保存的規格 checksum；
既有 store 不會寫入此 INVALID 規格。另覆蓋缺契約、錯鍵、節點不同、stale input checksum、
重複／缺漏來源、未知 SQL 欄位與 strict version。原始输入不被修改。

## 原生 Hop MergeJoin 證據

新增 `InspectJoinPlugin.java` 與 `ExecuteJoinProbe.java`，透過現有 Hop 2.12.0
plugin registry 取得真實 metadata，並由 LocalPipelineEngine 執行固定合成測試管線。
容器 `--network none`，僅允許 CSVInput／SortRows／MergeJoin／FilterRows／Dummy；
沒有資料庫、檔案輸出或任意程式節點。來源與 probe 唯讀掛載。

映像：`ai-etl-workbench-worker:dev`，本次 image ID
`sha256:665eb2e14db192580738fe0eb6168b82245ae56c43ddb2f5173b407c5fc6103c`。

已驗證八組（LEFT／INNER × 是否排除右側 null × 右側一般資料／全部 null），
加上發佈檔案檢查共 **9 passed（33.89s）**。逐筆比對保留重複列，不以筆數相同代替值相同：

- 相同鍵左 2 列、右 2 列 → 4 列，未自動去重。
- 區分 `A`／`a`／`A `，沒有 case folding 或 trim。
- 原生 MergeJoin 的 null 會匹配 null：左右 null payload 同時出現在輸出。
- 先以 FilterRows 排除右側 null 鍵，才符合 `NEVER_MATCH`。
- LEFT 保留無匹配的左列，右欄位為 null；INNER 不保留。
- 右側全部 null 被 Filter 排除、Join 接收到空資料流時，LEFT 仍保留全部左列，INNER 為 0 列。
- 檢查輸出 metadata 的四個欄位名称／順序與所有實際值。

首次四組測試因收集器誤把 row buffer 長度當成 metadata 欄數而失敗。
診斷明確取得 metadata=4、buffer=12 後，改為依 metadata 讀值，仍強制檢查欄位順序；
不是忽略 ETL 錯誤或修改標準答案。修正後先 5 passed，再擴充邊界至上述 9 passed。

此為**原生引擎語意證據，不是平台 Compiler 或 Vertica E2E 驗收**。
probe 管線由測試建構，尚非 V2 compiler 產物；單鍵字串已驗證，複合鍵／其他鍵型別仍需涵蓋。
編譯下一步必須產生「右側 null-key Filter → 各側 SortRows → MergeJoin」並綁定來源限定命名，
不能直接只產生 MergeJoin 就宣稱 `NEVER_MATCH` 正確。
